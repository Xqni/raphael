# Windows-Native Electron Orb — Research Findings

Research date: 2026-10-07. Scope: migrating Raphael's Electron overlay orb from WSL2/WSLg to a native Windows Electron build. Everything non-obvious is cited; anything I could not verify is marked **UNVERIFIED**.

---

## 1. Node on Windows: runtime vs. build-time

**Current Electron line (Oct 2026): Electron 44.x — Chromium 152.0.7977.54, V8 15.2, Node v24.18.1** (https://www.electronjs.org/blog/electron-44-0). Electron 40 shipped Node 24.11.1 (https://www.electronjs.org/blog/electron-40-0). So the **runtime Node inside modern Electron IS the Node 24 LTS line** — aligning the orb with Node 24 is correct.

- **Build tooling Node requirement:** electron-builder v27 requires **Node.js >= 22.12.0** (the version where `require(esm)` stabilized) and is now native-ESM (https://www.electron.build/docs/migration/v27-breaking-changes/, https://github.com/electron-userland/electron-builder/blob/master/MIGRATION.md). `@electron/rebuild` also requires Node >= 22.12 (https://github.com/electron/rebuild). Node 24 LTS satisfies both.
- **ABI (the thing that actually matters):** Electron has its own `NODE_MODULE_VERSION`, distinct from Node's. node-abi registry (https://github.com/electron/node-abi, `abi_registry.json`): **Electron 44 → ABI 149**, Electron 40 → 143, Electron 38 → 139; **Node 24 → ABI 137**. Any native module prebuilt for `node` ABI 137 will NOT load in Electron 44. Use `@electron/rebuild` (rebuilds against Electron headers) or prebuilds tagged for the `electron` runtime. Electron docs: https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules.
- **Windows-specific native-module gotcha:** node-gyp links against `node.dll`, but Electron ≥ 4 exports symbols from `electron.exe` — `win_delay_load_hook` must stay `true` in `binding.gyp` or you get "Module did not self-register" / "specified procedure could not be found" (same Electron docs page). `electron-rebuild` defaults to `--sequential` on Windows.
- **Launching from `C:\Program Files\nodejs`:** the `electron` npm package is a launcher — its postinstall downloads the prebuilt Electron dist (~100 MB, `ELECTRON_MIRROR` env overrides the download host) and `electron.exe` is executed with the app path. `npx electron .` resolves `node_modules/.bin/electron` first and works from any Node install on PATH. Plain `node.exe` **cannot** run an Electron app (different runtime + ABI); the reverse direction exists (`ELECTRON_RUN_AS_NODE=1 electron.exe` acts as Node). Gotchas: unsigned `electron.exe` triggers SmartScreen; on Windows child-process logs do NOT go to stderr — use `--enable-logging=file` (https://www.electronjs.org/docs/latest/api/command-line-switches). **UNVERIFIED:** exact `npx` behavior when the project has no local `electron` devDependency (prompt + network fetch).

## 2. Config path handling on Windows

Verified from official `app` docs (https://www.electronjs.org/docs/latest/api/app):

- `app.getPath('appData')` = **`%APPDATA%`** on Windows (`C:\Users\<u>\AppData\Roaming`). `app.getPath('userData')` = appData + app name (e.g. `%APPDATA%\Raphael\`). Docs convention: write app files into a **subdirectory** of `userData` to avoid colliding with Chromium's `Cache`, `GPUCache`, `Local Storage` dirs. `app.getPath('sessionData')` (cookies/cache/shaders) defaults to userData — docs recommend `app.setPath('sessionData', ...)` elsewhere if you don't need browser storage. `app.setPath(name, newPath)` works pre-`ready`; `LOCALAPPDATA` (per-machine, non-roaming) is the better home for caches/large state; there is no built-in `app.getPath('localAppData')` — read `process.env.LOCALAPPDATA` yourself.
- **Path resolution strategy for repo-root `config.yaml` + `config.d/*.yaml`:**
  1. Explicit override first: env var (e.g. `RAPHAEL_CONFIG_DIR`) or `process.argv` flag.
  2. **Dev layout:** `process.cwd()` / `app.getAppPath()` repo root — read `config.yaml` + sorted `config.d/*.yaml` directly (current behavior preserved).
  3. **Portable layout:** if `config.yaml` sits next to `process.execPath` (or in a `config/` folder beside it), treat that as the root — electron-builder has a first-class `portable` target (see §8).
  4. **Installed layout:** `%APPDATA%\Raphael\config.yaml` + `config.d\`, with packaged defaults shipped via `extraResources` (read-only) and user overrides layered on top. Asar is read-only at runtime, so never expect to write config inside the app dir.
  - Merge order: packaged defaults → user config dir → env overrides; keep `config.d` sorted lexicographically for determinism.
- `app.getPath('exe')` / `process.resourcesPath` (`assets` path docs) let you locate installed resources; `app.isPackaged` distinguishes dev vs installed.

## 3. Token/secret delivery on Windows

**Threat model, concrete:**

- **argv — never.** `Win32_Process.CommandLine` is readable by any user via WMI (`Get-CimInstance Win32_Process`) and shown in Task Manager → Details → "Command line" column. Extra Electron-specific leak: `app.requestSingleInstanceLock()` forwards the **second instance's argv into the first instance** via the `'second-instance'` event (https://www.electronjs.org/docs/latest/api/app#event-second-instance) — a token in argv leaks into the primary process's event handler too.
- **plain env — weak.** Env blocks are not exposed via WMI, but any process running as the **same user** can read another process's environment with `PROCESS_VM_READ` (no admin required for same-user, non-protected processes). Same-user malware reads env trivially; it protects against *other users* and casual inspection only.
- **Patterns, ranked for a single-user box:**
  1. **stdin handoff (best for per-launch delivery):** launcher writes the token to the child's stdin (`spawn(..., {stdio:['pipe',...]}); child.stdin.write(token)`). Never appears in any OS query surface. Caveat on Windows: **GUI-subsystem processes launched from Explorer/shortcuts have invalid stdin** — stdin delivery only works when a launcher script/terminal/agent spawns the orb. Dev-loop: supervisor pipes it; production: persist after first handoff (see safeStorage).
  2. **Named pipe:** Node's `net` module supports Windows named pipes (`\\.\pipe\<name>`) for both server and client on Windows. Create the pipe **before** spawning the child with an explicit `SECURITY_ATTRIBUTES` DACL granting only the current user SID — otherwise there is a pipe-squatting race where another process creates `\\.\pipe\` name first. Pipe ACLs are the 0600-equivalent for IPC; protects against other users; a same-user hostile process can still connect. (Windows named-pipe security model: https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipes.)
  3. **0600-equivalent file + `icacls`:** NTFS inheritance already DACLs `%APPDATA%\*` to the owner + SYSTEM + Administrators — an ACL'd config/token file is "user-only" by default. Hardening: `icacls token.txt /inheritance:r /grant:r "%USERNAME%":F "SYSTEM":F` (icacls: https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/icacls). **Limitation: ACLs do NOT stop other processes running as the same user** — they're a multi-user/backup boundary, not a same-user boundary. Plaintext at rest.
  4. **Windows Credential Manager:** `cmdkey /Generic:Raphael /user:orb /pass:...` stores in the per-user vault (https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/cmdkey). **`cmdkey` cannot read values back** — reading requires the Credential Management API (`CredRead`) via a native module or PowerShell P/Invoke; there is **no Electron built-in**. Best for human-entered long-lived secrets.
  5. **DPAPI (`ProtectedData`):** .NET `ProtectedData.Protect(data, entropy, DataProtectionScope.CurrentUser)` — https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.protecteddata. User-scope blobs decrypt only under the same logon credentials; pass an app-specific `entropy` as a salt. **DPAPI is not a same-user sandbox** — any same-user process can also decrypt.
  6. **Electron `safeStorage` (recommended at-rest store):** official docs — Windows keys are generated via **DPAPI**; content is "protected from other users on the same machine, **but not from other apps running in the same userspace**" (https://www.electronjs.org/docs/latest/api/safe-storage, https://github.com/electron/electron/blob/main/docs/api/safe-storage.md). `safeStorage.isEncryptionAvailable()`, `encryptString`/`decryptString`, store base64 blob under `userData`.
- **Concrete recommendation for the orb:** (a) dev/agent handoff = stdin or user-DACL'd named pipe at launch — nothing touches argv/env; (b) production persistence = first-run handoff → `safeStorage.encryptString` → `%APPDATA%\<app>\secrets.bin` (already DACL'd by inheritance; add `/inheritance:r` if paranoid); (c) never log the token; (d) remember the `'second-instance'` argv forwarding path; (e) treat safeStorage as backup-safe (ciphertext) but not malware-safe (same-user decryptable — same as DPAPI).

## 4. Always-on-top + click-through + transparency (Windows)

- **`setAlwaysOnTop(flag, level, relativeLevel)`** — docs: `level` is macOS+Windows; values `normal`, `floating`, `torn-off-menu`, `modal-panel`, `main-menu`, `status`, `pop-up-menu`, `screen-saver`; `relativeLevel` is macOS-only (https://www.electronjs.org/docs/latest/api/browser-window#winsetalwaysontopflag-level-relativelevel). **Verified in Electron source** (`shell/browser/native_window_views.cc`, `SetAlwaysOnTop`): on Windows every always-on-top window is topmost; the level names **`floating`..`status` additionally place the window *behind the taskbar*** (`behind_task_bar_` → `MoveBehindTaskBarIfNeeded`), while **`pop-up-menu`/`screen-saver` sit above the taskbar**. So on Windows the level is an above/below-taskbar switch, not distinct z-bands. Z-order vs *other* topmost windows follows normal HWND topmost ordering.
- **`setFullScreenable(false)`**, **`setSkipTaskbar(true)`** exist (Windows impl of skipTaskbar = `ITaskbarList::DeleteTab` — verified in source; NOT `WS_EX_TOOLWINDOW`). **`focusable: false`** on Windows sets **`WS_EX_NOACTIVATE`** and implies skipTaskbar (verified in source + BaseWindow docs). Alt-Tab exclusion is **NOT guaranteed** by DeleteTab/NOACTIVATE — the reliable Win32 tool is `WS_EX_TOOLWINDOW`, which Electron does not set via these APIs (prototype/possibly native-module fallback; see §8 & Open Questions).
- **`setIgnoreMouseEvents(true, { forward: true })`** — docs: `forward` is supported on **macOS and Windows** (https://www.electronjs.org/docs/latest/api/browser-window). Verified source (`NativeWindowViews::SetIgnoreMouseEvents`): on Windows `ignore=true` sets **`WS_EX_TRANSPARENT | WS_EX_LAYERED`**; `forward` calls `SetForwardMouseMessages(forward)` — forwarding is forced off when not ignoring. `forward: true` re-enables `mousemove`/`mouseenter`/`mouseleave` so the orb can hover-detect and toggle interactivity. **Known bugs:** forwarding broken when non-Electron windows are focused (#33281, https://github.com/electron/electron/issues/33281); forwarding spam/broken in Electron 22 (#30808, https://github.com/electron/electron/issues/30808); a hidden helper window using `forward` affected *other apps'* drag behavior (#35030, https://github.com/electron/electron/issues/35030). Historically flaky — treat hover-forward as "works on current stable, needs regression tests".
- **Click-through of transparent areas:** Electron's Custom Window Styles docs still say "You cannot click through the transparent area" (https://www.electronjs.org/docs/latest/tutorial/custom-window-styles) — this is **outdated**; `setIgnoreMouseEvents` is the supported path and issue commenters confirm click-through works in Electron ≥ 27. The **legacy workaround** `app.disableHardwareAcceleration()` / `--disable-gpu-compositing` (which made clicks fall through transparent pixels) **broke in Chromium 139 / Electron 38** (2025) — restoring it requires `--disable-direct-composition` + `disableHardwareAcceleration`, forcing the GDI path and **destroying GPU compositing** (#48064, https://github.com/electron/electron/issues/48064, Chromium CL 6106730 "Use DXGI swapchains and DCOMP visuals in software mode"). **Do not use that workaround for a WebGL orb** — it kills WebGL performance.
- **DWM shadow / frame suppression:** `thickFrame` (Windows-only, default `true`) — docs: `WS_THICKFRAME` "adds the standard window frame. Setting it to **false will remove window shadow and window animations**, and disable window resizing via dragging edges" (https://www.electronjs.org/docs/latest/api/structures/base-window-options). This is the native replacement for the WSLg `topmost.ps1` shadow-strip hack. Also relevant: `transparent` on Windows **only works if the window is frameless**; `hasShadow` option exists; `titleBarStyle: 'hidden'` + `roundedCorners: false` + `backgroundMaterial: 'none'` + `backgroundColor: '#00000000'` is the modern transparent recipe.
- **Known transparent+always-on-top bugs:** phantom titlebar reappears on blur for `transparent:true` + `titleBarStyle:'hidden'` (#39959, fixes landed Electron 28.1.1 but reports persisted into v31–v37 for some setups, https://github.com/electron/electron/issues/39959); **white inactive-frame corners on Win11** when a transparent frameless window loses focus (DWM draws inactive frame decoration over transparent pixels; issue open on recent Electron, #51662, https://github.com/electron/electron/issues/51662); toggling `setResizable()` can re-add `WS_THICKFRAME` and **destroy transparency** (PR #51175, https://github.com/electron/electron/pull/51175); transparent windows are not resizable (docs); not transparent while DevTools open (docs); cannot maximize via system menu (PR #28207); DWM must be enabled (docs — "transparent windows will not work when DWM is disabled").
- **Z-order vs games:** Chromium's native occlusion tracker explicitly treats **transparent windows as non-occluding** (https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/windows_native_window_occlusion_tracking.md), so apps *below* the orb keep rendering. Exclusive-fullscreen (non-DWM-composited) games may bypass topmost desktop windows entirely; borderless-windowed games are DWM-composited and a topmost orb will draw over them — **behavior vs actual games is UNVERIFIED / needs prototype.**
- **Focus-steal:** `WS_EX_TRANSPARENT` means clicks pass through and don't activate the orb; but a *focusable* orb can still be activated by other paths. Overlay recipe: `alwaysOnTop: true` + `focusable: false` (→ `WS_EX_NOACTIVATE` + no taskbar tab) + `setIgnoreMouseEvents(true, { forward: true })` + `thickFrame: false`.

## 5. Multi-monitor + DPI

- **`screen` module (verified docs, https://www.electronjs.org/docs/latest/api/screen):** `getAllDisplays()`, `getPrimaryDisplay()`, `getDisplayNearestPoint(point)`, `getDisplayMatching(rect)`; conversions **`screenToDipPoint` / `dipToScreenPoint` (Windows, Linux)** and **`screenToDipRect(window, rect)` / `dipToScreenRect(window, rect)` (Windows only)** — rect versions scale "relative to the display nearest to `window`" (pass `null` to use the display nearest the rect). Events: `'display-added'`, `'display-removed'`, `'display-metrics-changed'` (changedMetrics ∈ bounds, workArea, scaleFactor, rotation).
- **DIP vs physical:** all `BrowserWindow` geometry (`setPosition`, `getBounds`, `setBounds`) and `screen` point APIs are **DIP** (DPI-virtualized) coordinates; physical pixels = DIP × `Display.scaleFactor`. Docs explicitly define the two coordinate kinds (screen page preamble).
- **Per-monitor DPI awareness:** there is **no `app.enableHostRuntime` API** — that name does not appear anywhere in Electron's `app` docs (checked current docs). Electron inherits **Chromium's** process DPI awareness; modern Chromium/Chrome declares **PerMonitorV2 by default** (CefSharp issue: "Chromium now sets the DPI Awareness to Permonitorv2 by default. You can override this via app.manifest or via programmatic call", https://github.com/cefsharp/CefSharp/issues/2927; Microsoft manifest docs: https://learn.microsoft.com/en-us/windows/win32/hidpi/setting-the-default-dpi-awareness-for-a-process). Historical Electron issues that drove per-monitor support: #5429, #8533, #10862 (windows start out-of-bounds on mixed-DPI multi-monitor, https://github.com/electron/electron/issues/10862). **UNVERIFIED:** the exact DPI-awareness context of Electron 44's shipped `electron.exe` on the target box — check empirically: `Get-Process -Name electron | Select DPIAwareness` (Windows 10 1607+).
- **The mixed-DPI trap:** when a window straddles two monitors with different `scaleFactor`s, Windows sends `WM_DPICHANGED` and Chromium applies **one** scale to the whole window; DIP positions on the "other" monitor therefore shift, and a persisted DIP coordinate can land on the wrong display or off-screen after a monitor/scale change (#10862 above).
- **Persist-dragged-position pattern:** on `'move'` (DIP coords), debounce and store `{x, y}` **plus** `display.id` + `scaleFactor` snapshot. On restore: `screen.getDisplayNearestPoint({x, y})`; if that `display.id` no longer exists (`'display-removed'` / `display-metrics-changed` with changedMetrics incl. `scaleFactor`), re-clamp into `display.workArea` (e.g. anchor orb at work-area corner on primary). For exact physical placement at runtime use `dipToScreenRect(null, rect)` then `setPosition` with the converted values, or `screenToDipPoint` when receiving raw `GetCursorPos` data from a native module. `win.getBounds()` is DIP — mixing it with physical-pixel native APIs (e.g. `GetWindowRect` via `win.getNativeWindowHandle()`) without conversion is the classic bug.

## 6. GPU flags for a transparent WebGL overlay on Windows

- **Baseline:** `frame: false` + `transparent: true` (transparent requires frameless on Windows, docs) + `backgroundColor: '#00000000'` (docs: "#AARRGGBB alpha supported if transparent is set to true", BaseWindow options). Keep hardware acceleration ON — `app.disableHardwareAcceleration()` would kill WebGL GPU rendering (and its old click-through side effect is broken anyway, §4). Inspect state with `app.getGPUFeatureStatus()` / `app.getGPUInfo('complete')` (Electron APIs, https://www.electronjs.org/docs/latest/api/app).
- **Occlusion throttling (critical for overlays):** Chromium stops rendering + throttles JS when its native window-occlusion tracker deems a window covered (https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/windows_native_window_occlusion_tracking.md). Defense: `app.commandLine.appendSwitch('disable-features', 'CalculateNativeWinOcclusion')` — confirmed effective in Electron (#29280, https://github.com/electron/electron/issues/29280). **Gotcha:** `appendSwitch('disable-features', X)` **clobbers** any pre-existing `disable-features` value (Chromium switches are keyed; documented in a code review of a real Electron app, https://github.com/NousResearch/hermes-agent/pull/83540) — merge/dedupe manually. **Whether Electron 44 enables occlusion tracking by default is UNVERIFIED** (Chromium once proposed making it opt-in for embedders — https://groups.google.com/a/chromium.org/g/embedder-dev/c/ZF3uHHyWLKw — but current Electron-era bug reports show it active); setting the switch explicitly is cheap insurance.
- **Backgrounding flags (cross-platform, Electron-documented):** `--disable-renderer-backgrounding` ("Prevents Chromium from lowering the priority of invisible pages' renderer processes", https://www.electronjs.org/docs/latest/api/command-line-switches); `--disable-backgrounding-occluded-windows`; and per-window `webPreferences: { backgroundThrottling: false }` (default `true`; docs note disabling keeps visibility 'visible' and frames drawn even when minimized/hidden/occluded — BrowserWindow "Page visibility" section). **Trade-off:** a real Electron app measured that a *static, global* `backgroundThrottling: false` caused **~20% idle CPU burn**, and chose scoped toggling instead (https://github.com/NousResearch/hermes-agent/pull/83540) — disable throttling **only for the orb window**.
- **Raster/compositing switches:** `--enable-gpu-rasterization` (GPU raster for compositor/canvas; cross-platform Chromium switch — full Chromium switch list: https://peter.sh/experiments/chromium-command-line-switches/, official discovery path via `about://flags` + `flag-metadata.json` per Electron docs), `--enable-zero-copy`, `--disable-gpu` (software rendering — breaks GPU WebGL; cross-platform), `--in-process-gpu` (merges GPU process into browser; crash blast-radius trade-off). Electron also documents `--force_high_performance_gpu` / `--force_low_power_gpu` (multi-GPU machines).
- **ANGLE backend selection:** `--use-gl=angle --use-angle=d3d11` — official ANGLE docs: `--use-angle=d3d11` = "Direct3D 11 renderer, **Windows only**" (https://chromium.googlesource.com/angle/angle/+/HEAD/doc/DebuggingTips.md). Modern Chromium on Windows already defaults to ANGLE/D3D11 — set these only when debugging driver-specific WebGL issues. `--use-angle=gl` / `--use-angle=vulkan` are the alternatives.
- **Transparent-window + GPU known issues:** transparency not respected (black/gray background instead of transparent) on some setups (#40515, https://github.com/electron/electron/issues/40515); Chromium 139+ moved Windows presentation to DXGI swapchains + DirectComposition visuals, which changed transparent-window behavior (#48064 discussion). **Cross-platform vs Windows-only:** `CalculateNativeWinOcclusion`, `--use-angle=d3d11`, `--disable-direct-composition`, `--force_high_performance_gpu` are Windows-relevant; the backgrounding/rasterization flags are cross-platform. `--disable-features=CalculateNativeWinOcclusion` must also be merged with any launcher-provided disable-features value (§ above).

## 7. Measuring idle CPU/GPU on Windows (and WSLg's added cost)

- **CPU — `typeperf`:** `typeperf "\Process(electron*)\% Processor Time" -si 2 -sc 10` (https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/typeperf). `% Processor Time` needs ≥2 samples to compute a delta (PDH semantics, https://learn.microsoft.com/en-us/windows/win32/perfctrs/collecting-performance-data). Counter instance names truncate to 15 chars and get `_1`, `_2` suffixes; multiple `electron` processes (main/GPU/renderer) each appear — sum them, or use `_Total`.
- **CPU — PowerShell:** `Get-Counter '\Process(electron*)\% Processor Time' -SampleInterval 2 -MaxSamples 5`. `Get-Process`'s `CPU` column is *cumulative seconds* — compute deltas yourself. **In-app:** `app.getAppMetrics()` returns `ProcessMetric[]` with per-process CPU/memory (Electron docs) — good for self-reporting without external tools.
- **GPU:** Windows 10 1809+ exposes **`\GPU Engine(*)\Utilization Percentage`** — instance names encode PID/luid/engine (e.g. `pid_1234_luid_0x..._phys_0_eng_0_engtype_3D`); sum all engine instances for your PID. Correlating PID via counter instances is documented in Microsoft Q&A PDH guidance (https://learn.microsoft.com/en-us/answers/questions/5641645/how-to-get-the-special-process-gpu-usage-with-the) and Stack Overflow PDH examples; the same counters feed Task Manager's GPU view (gamedev.stackexchange.com Q on GPU Engine counters). Companion memory counter: `\GPU Adapter Memory(*)\Dedicated Usage`. **UNVERIFIED:** exact `Get-Counter` wildcard pattern for per-PID GPU engines on the target Windows build — prototype the instance-name filter.
- **ETW / WPR (gold standard, heavy):** `wpr -start GPU -filemode` → run workload → `wpr -stop trace.etl`, analyze in Windows Performance Analyzer (https://learn.microsoft.com/en-us/windows-hardware/test/wpt/). Use when counter-level numbers are ambiguous; overkill for routine idle checks.
- **Healthy idle target (ESTIMATE — must be measured):** a 280×280 transparent WebGL orb at 30 fps on a modern iGPU/dGPU should cost low-single-digit % CPU across processes and low single-digit % GPU-engine utilization. Anything >5–10% sustained CPU at idle is a red flag (throttling-off burn, occlusion loops, or shadow/compositor fights).
- **WSLg's added cost — documented numbers:** Microsoft's WSLg README: vGPU interops with the Weston compositor **through system memory** — "rendered data is copied from VRAM to system memory before being presented to the compositor within WSLg, and uploaded onto the GPU again on the Windows side… **performance penalty proportionate to the presentation rate. At very high frame rates such as 600fps on a discrete GPU, that overhead can be as high as 50%**. At lower frame rate or on integrated GPU, performance much closer to native" (https://github.com/microsoft/wslg/blob/main/README.md). Architecture (msrdc/RDP client + Weston RAIL/VAIL + FreeRDP + virtio-fs shared memory): https://devblogs.microsoft.com/commandline/wslg-architecture/. Independent measurement (Tom Fenton, Virtualization Review): Unigine Heaven under WSLg averaged **17.3 fps vs 43.4 fps native** on a Radeon Pro WX3200 (~60% slower); glmark2 score 423 with GPU up to 48% (https://virtualizationreview.com/articles/2022/07/01/wslg-deeper-dive.aspx). For a *small 30fps overlay* the absolute cost is modest, but every frame still crosses: GPU→sysmem→Weston→virtio-gpu→msrdc→Windows DWM, plus input/cursor relay — and the shadow-margin/topmost hacks in the current setup are themselves symptoms of fighting the RDP presentation layer. A native window composes directly with DWM; none of that path exists.

## 8. Electron-on-Windows pitfalls for this exact use case

- **The combo `frame:false + transparent:true + alwaysOnTop`** is supported on Windows (transparent *requires* frameless — BaseWindow docs). Residual minefield: phantom titlebar on blur (#39959), white DWM inactive-frame corners on focus loss (#51662), transparency loss via `setResizable` toggles (#51175), non-resizable-by-design transparent windows, DevTools breaks transparency (all cited in §4). For a small always-focused orb most of these are low-risk, but #51662 (focus loss) is directly in the orb's threat model.
- **Snapping / Alt-Tab:** `win.snapped` (Windows, readonly) tracks Snap state; `setFullScreenable(false)` prevents maximize-button fullscreen; `resizable:false` blocks edge-resize. **Alt-Tab visibility is NOT solved by `setSkipTaskbar`** (verified: it only calls `ITaskbarList::DeleteTab`) — `focusable:false` adds `WS_EX_NOACTIVATE` (verified in source) which prevents activation but does not provably exclude the window from the Alt-Tab switcher; the Win32 answer is `WS_EX_TOOLWINDOW` (https://learn.microsoft.com/en-us/windows/win32/winmsg/extended-window-styles), reachable only via a native module. **Needs prototype.**
- **`app.setAppUserModelId(id)`** (Windows): sets the Application User Model ID — required for correct taskbar grouping, notifications, and Jump Lists; also serves as the default registry value name for login items (https://www.electronjs.org/docs/latest/api/app#appsetappusermodelidid-windows, https://learn.microsoft.com/en-us/windows/win32/shell/appids). Set it early, before showing notifications.
- **Single-instance:** `app.requestSingleInstanceLock(additionalData)` — returns `false` in the second instance, which should quit; primary gets `'second-instance'` with `argv`, `workingDirectory`, `additionalData` (JSON; docs note argv order may change and extra Chromium args get appended — pass state via `additionalData`, not argv; 32 MB message cap on macOS/Linux). Also `app.hasSingleInstanceLock()` / `app.releaseSingleInstanceLock()`.
- **Autostart:** `app.setLoginItemSettings({ openAtLogin, path, args, enabled, name })` — Windows impl writes the per-user **Run registry key** (`HKCU\...\CurrentVersion\Run`, value name defaults to AppUserModelId) plus the **StartupApproved** key so `enabled` toggles it in Task Manager/Windows Settings (docs mention this key explicitly). Alternatives: **Startup folder** shortcut (same UX, user-visible/editable) vs **Task Scheduler** (schtasks: logon trigger + delay, conditions, run-as-user; visible in `taskschd.msc`; what supervisor-style apps use when Run-key timing/conditions aren't enough — writing the task, not running schtasks, is the deliverable per project convention). For an orb that must survive late network/agent bring-up, Task Scheduler with a logon delay is the robust choice; Run-key is the zero-dependency choice.
- **Packaging:** electron-builder Windows targets: `nsis` (installer; per-user/per-machine; auto-update friendly), `nsis-web`, `portable` (single exe, no install — fine for an orb, userData still `%APPDATA%`), `appx`/`msix`, `msi`, `squirrel`, `zip`/`7z` (https://www.electron.build/docs/win). v27 notes: Windows signing config moved under `win.sign`, toolset defaults changed, **building Windows targets on macOS now needs Wine** — irrelevant if building on the Windows box itself. SmartScreen punishes unsigned exes — budget for signing if distribution matters. For dev-loop simplicity: `electron .` via npx; for the user-facing install: NSIS per-user or portable.
